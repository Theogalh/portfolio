Ce que ça fait

Chaque projet perso commençait par la même soirée de mise en place : arborescence, réglages, client Redis, health check, un script de déploiement, un workflow. theoproject réduit tout ça à une commande, et garde le résultat cohérent d’un projet à l’autre pour que passer de l’un à l’autre ne coûte rien.

Trois variantes

Un simple paquet Python, un CLI Click installable avec découverte de plugins, ou une application FastAPI complète en couches avec rendu serveur.

Surcouches de stockage

Ajoutez Redis, SQLite ou les deux. Chacune apporte un client, ses réglages et un health check adossé au stockage.

Couche de déploiement

La variante FastAPI livre une unité systemd, une config nginx, un script d’installation pour un LXC vierge et un script de déploiement pour chaque push.

Snippets versionnés

Des modules réutilisables (e-mail SMTP, stockage de fichiers S3) tirés de tags GitHub, épinglés dans un lockfile, mis à jour à la demande.

Harnais Claude Code

Chaque projet livre .claude/ : commandes, sous-agents, skills et hooks d’exemple, empilés selon la variante.

Jetons de design

--design ajoute les jetons partagés, les composants et le gabarit de base pour que l’interface s’accorde au reste.

Du dossier vide au premier déploiement

uv tool install le CLI une bonne fois.
theoproject create <name> --fastapi --redis dans un dossier vide.
Posez quatre secrets SSH sur le dépôt GitHub.
Lancez deploy/setup.sh une fois sur le LXC en root.
Push sur main : job de contrôle, puis job de déploiement via SSH.
Ajoutez des snippets au besoin : theoproject add smtp.

Architecture

Les gabarits sont des dossiers fusionnés dans l’ordre. Une variante, c’est la base plus sa couche ; la couche web s’ajoute pour --fastapi.

templates
theoproject/
  templates/           base: .claude/ harness, ADR scaffolding, .gitignore
  templates_web/       --fastapi only: deploy/, systemd, nginx, deploy.yml
  templates_simple/    pure-Python package
  templates_fastapi/   modules, storage interface, web SSR
  templates_cli/       Click group, plugin loader, 4-layer modules
  snippets/
    smtp/    snippet.toml · src/
    storage/ snippet.toml · src/
  cli.py               create · cli new · add · update · list · release

Décisions

  • Des couches, pas des forksUne variante ne recopie jamais une autre variante. Corriger la base corrige tous les projets générés ensuite.
  • Un seul contrat de stockageChaque surcouche implémente StorageInterface (close, ping). Deux surcouches donnent gratuitement un /health combiné.
  • Les snippets sont publiés, pas collésUn snippet vit dans ce dépôt, porte un tag par version, et atterrit dans le theolib/ d’un projet avec ses dépendances fusionnées dans pyproject. Le lockfile est commité.
  • Le hook impose l’incrémentUn hook pre-commit refuse une modification sous src/ sans nouvelle version dans snippet.toml, et refuse une version qui existe déjà comme tag.
  • Surface de déploiement minimaleUn workflow, quatre secrets SSH. Le serveur tire, synchronise, redémarre et vérifie la santé. Rien d’autre à configurer.
  • Prochaines étapes arrêtéesUn SSO enfichable via un broker OIDC, un contrat d’exécution par palier de déploiement et une bibliothèque de rapport de bug sont des directions décidées, pas des fonctionnalités livrées.

Le lancer

shell 
uv tool install git+ssh://git@github.com/Theogalh/theoproject.git
mkdir invoices && cd invoices
theoproject create invoices --fastapi --redis --design \
  --user inv --domain invoices.theogalh.dev
theoproject add storage
