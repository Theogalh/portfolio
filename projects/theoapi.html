Un seul compte pour toutes les applications.

TheoAPI est la couche d’identité sous tout le reste : on se connecte une fois, et chaque application décide de ce que ce compte a le droit de faire.

Ce que ça fait

Chaque application de ce site a besoin d’utilisateurs, et aucune ne devrait avoir à réimplémenter la connexion. TheoAPI émet les jetons, détient les comptes et les rôles, laisse chaque application définir ses propres rôles et déléguer l’administration à des personnes précises, et donne aux utilisateurs une console qui n’affiche que ce qu’ils ont le droit d’ouvrir.

Trois façons de se connecter

E-mail et mot de passe avec vérification et réinitialisation, OAuth Google, ou une connexion Jellyfin. Toutes aboutissent à la même paire de jetons.

Rôles par application

Une application déclare ses rôles. Un utilisateur peut être administrateur d’une application sans aucun droit sur la plateforme.

Console

Un tableau de bord listant les applications que vos rôles autorisent, plus des écrans d’administration pour les utilisateurs, les applications et les rôles.

Journal d’audit

Toute action d’administration liée à une application est journalisée ; les actions de plateforme sont journalisées sur l’application plateforme.

Clés d’API et jetons bearer

Les applications et les scripts s’authentifient par un en-tête ; les navigateurs par un cookie et un jeton CSRF.

Liaison Jellyfin

Les comptes du serveur média peuvent être reliés aux comptes TheoAPI, pour qu’une seule identité couvre les applications et les médias.

Une connexion, étape par étape

Les identifiants arrivent : en-tête ApiKey, en-tête Bearer, ou le cookie theoapi_token.
Le principal est résolu ; les drapeaux vérifié, supprimé et réinitialisation forcée sont contrôlés.
Les rôles de plateforme sont chargés depuis principal_roles.
Les rôles par application viennent de user_app_roles quand la route est liée à une application.
Les requêtes par cookie doivent aussi porter l’en-tête CSRF en double soumission sur les méthodes non sûres.
Le jeton d’accès expire au bout de 60 minutes ; le rafraîchissement émet une nouvelle paire et révoque selon la politique.

Architecture

Un module par domaine, chacun sur quatre couches. Les préoccupations transverses vivent dans src/common.

layout
src/app/       app factory, settings, router assembly
src/common/    auth middleware · RBAC deps · CSRF · rate limit · hashing · email · Jellyfin client
src/data/db.py all SQL, one connection per call
src/modules/
  auth/        login · register · refresh · logout · google · jellyfin
  users/       profile, verification, password reset
  apps/        app registry, app roles, user-app roles
  admin/       platform and app-scoped admin
  toolbox/     stub
src/web/       Jinja page routes under /web, redirect instead of 401
templates/ · sdk/theo_ui/ · scripts/migrate_db.py · scripts/seed_admin.py

Décisions

  • Des principaux, pas des utilisateursTout ce qui peut agir est un principal : un utilisateur, un jeton bearer de développement, une clé d’API. Les rôles s’attachent aux principaux, donc les scripts et les applications obtiennent des permissions sans faux utilisateur.
  • Deux couches RBAC, tenues séparéesLes rôles de plateforme (super_admin · admin · user · app) et les rôles par application avec un drapeau is_admin. super_admin contourne les contrôles applicatifs partout.
  • Trois portes, un seul modèle de jetonLes connexions par mot de passe, Google et Jellyfin émettent toutes la même paire bearer/refresh, vérifient automatiquement, et relient automatiquement par e-mail ou identifiant Jellyfin.
  • Aucun secret n’est stocké en clairLes jetons et les clés sont hachés en sha256 au repos ; les mots de passe utilisent PBKDF2 avec un sel aléatoire. Les jetons de développement peuvent être injectés depuis l’environnement, pour les tests locaux uniquement.
  • Du CSRF seulement là où il y a des cookiesL’authentification par cookie s’accompagne d’un cookie et d’un en-tête CSRF en double soumission. L’authentification par en-tête en est dispensée, puisqu’elle ne repose pas sur les cookies.
  • Gestion de schéma sans surpriseCREATE TABLE IF NOT EXISTS au démarrage, plus un script de migration additif protégé par des contrôles de colonnes. Pas d’ORM, pas de framework de migration.
  • Les erreurs ont une seule formeLes services lèvent ValueError ; les contrôleurs les traduisent en HTTP. Les routes web redirigent vers la connexion plutôt que de lever un 401.
