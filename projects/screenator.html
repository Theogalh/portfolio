Ce que ça fait

Un joueur poste la capture d’écran d’un jeu vidéo. Les autres se dépêchent de le nommer. La première bonne réponse marque le point et choisit la capture suivante. Screenator tient les manches, les scores et les règles d’équité pour que le groupe n’ait plus qu’à jouer.

Natif Discord

Des commandes slash sous un préfixe configurable. Un admin enregistre un salon, lance une partie, et chaque salon fait tourner sa propre partie indépendante avec son propre classement.

Salons web

Créez un salon avec un compte, ou rejoignez anonymement depuis un lien d’invitation. Chat en direct, classement en direct, et le propriétaire du salon peut exclure un joueur.

Manches équitables

Après une manche avec un gagnant, seul le gagnant peut poster la capture suivante. Seul l’auteur de la manche peut désigner un gagnant à la main.

Réponses tolérantes

Une faute de frappe ne fait pas perdre la manche : au-delà d’une longueur minimale, les réponses sont comparées à la solution de façon approchée.

Délais

Si personne ne trouve le jeu avant le délai propre au salon, le bot clôt la manche et révèle la réponse.

Bilingue

L’interface web bascule entre l’anglais et le français depuis la barre de navigation.

Une manche, étape par étape

Un joueur poste une capture avec /scr round ou depuis le salon.
Les joueurs tapent leurs propositions dans le chat.
Chaque proposition est comparée à la solution, exactement ou de façon approchée.
Première bonne réponse : +1 point, la manche se ferme, le gagnant poste la suivante.
Aucune trouvaille avant le délai : le bot révèle le jeu, n’importe qui peut poster la suivante.
/scr stop termine la partie et affiche le classement final.

Architecture

Un paquet, trois points d’entrée. Les trois partagent un même Redis et une même interface de stockage.

layout
screenator/
  bot/          discord.py cogs, slash commands
  web/          FastAPI app, WebSocket rooms
    templates/  Jinja2 pages + partials (navbar, footer)
  playground/   matching sandbox service
  storage/      StorageInterface + DTOs (Game, Round, Leaderboard)
  cache/        Redis implementation, key builder
deploy/
  screenator.service · screenator-web.service · screenator-playground.service
  nginx/screenator.conf · deploy.sh · sudoers-screenator

Décisions

  • Une interface de stockage, des DTO typésLa logique de jeu ne voit que StorageInterface et des dataclasses. Redis est le backend actuel ; SQLite ou Postgres peut le remplacer sans toucher à un seul gestionnaire de commande.
  • Trois services, une base de codeLe bot, l’application web et le playground sont des unités systemd distinctes sur le même dépôt. Ils se déploient ensemble et partagent la configuration.
  • Les joueurs anonymes sont de plein droitUn jeton d’invitation crée une identité name#1234 ; un identifiant de synchronisation la transporte d’un appareil à l’autre. Les joueurs connectés retrouvent leurs salons côté serveur.
  • Le bucket n’est jamais publicLes images sont servies via des jetons de proxy avec leur propre TTL. Les identifiants Scaleway acceptent aussi les alias d’environnement natifs.
  • Le même contrôle en local et en CImake check lance le formatage, le lint, les types et les tests. La CI l’exécute plus un import de fumée côté web, puis déploie au push sur master.
