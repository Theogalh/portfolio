Ce que ça fait

La plupart des téléchargeurs vous font patienter devant un spinner et vous rendent le fichier entier. ytp analyse d’abord l’URL, vous laisse choisir l’audio ou la vidéo et un segment, lance le travail en arrière-plan et vous prévient quand le fichier est prêt. Le même moteur est exposé à Claude via MCP.

Analyser d’abord

Collez une URL et obtenez le titre, la durée et les formats disponibles avant de lancer quoi que ce soit.

Audio ou vidéo

mp3 et m4a pour l’audio, mp4 et webm pour la vidéo. L’identifiant de format vient directement de l’analyse.

Découper

Indiquez un début et une fin pour ne garder que le passage voulu. La coupe se fait côté serveur.

Progression en direct

La page s’abonne au travail et se met à jour jusqu’à ce que le fichier soit prêt ou que le travail échoue.

Depuis un assistant

Trois outils MCP : récupérer les infos pour un téléchargement simple, ouvrir l’éditeur de découpe pour choisir, télécharger et récupérer une URL.

Nettoyé

Les fichiers vivent sous l’identifiant du travail et sont supprimés à l’expiration. Un fichier disparu est signalé comme tel, pas comme une erreur.

Un téléchargement, étape par étape

POST /api/videos/info avec l’URL.
Choisissez un identifiant de format, éventuellement un début et une fin.
POST /api/downloads renvoie 202 et un identifiant de travail.
Le worker lance yt-dlp (et ffmpeg pour les découpes) et met à jour le travail dans Redis.
La page suit /events jusqu’au statut prêt ou échoué.
GET /file diffuse le résultat avec le bon type de média.

Architecture

Quatre modules sur le squelette theoproject. Le serveur MCP appelle les mêmes services que les contrôleurs HTTP.

layout
app/          config · main · router · limiter
modules/
  videos/     POST /videos/info — yt-dlp extract_info
  downloads/  jobs: create · status · events (SSE) · file
  metrics/    OpenTelemetry counters
  health/     Redis ping
mcp/          get_video_info · open_trim_editor · download_video
cache/        RedisClient + key builder · job tracker
data/{job_id}/  downloaded artifacts (retention)
web/ templates/ static/ deploy/ .github/

Décisions

  • Un téléchargement est un travailLa requête renvoie 202 Accepted immédiatement. yt-dlp ne tourne jamais dans une requête HTTP, donc une source lente ne peut pas bloquer l’application.
  • SSE plutôt que WebSocketLa progression ne circule que dans un sens. SSE, c’est du HTTP ordinaire, ça se reconnecte tout seul, et X-Accel-Buffering: no empêche nginx de le tamponner.
  • 410 pour les fichiers nettoyésUn travail qui a existé mais dont l’artefact a été supprimé répond 410 Gone ; un travail qui n’est pas prêt répond 409. Le client peut distinguer les deux cas.
  • Une couche de service, deux portes d’entréeLes contrôleurs HTTP et les outils MCP appellent tous les deux VideoService et DownloadService. Corriger un bug le corrige des deux côtés.
  • Limites de débit en bordure d’application20/min sur l’analyse, 10/min sur les téléchargements, par IP, appliquées dans les décorateurs de contrôleur.
