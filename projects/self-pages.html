GitHub Pages, sur ma machine, pour des dépôts privés.

Poussez sur un dépôt privé et le site statique est en ligne quelques secondes plus tard. Un webhook tire, un lien symbolique bascule, nginx sert. Cette page est déployée par lui.

Ce que ça fait

GitHub Pages ne sert pas les dépôts privés sur un forfait personnel, et je ne voulais ni étape de build ni tiers dans la boucle pour une poignée de sites statiques. self-pages est la plus petite chose qui marche : GitHub lui signale qu’un dépôt a bougé, il clone le nouveau commit à côté de l’ancien, et bascule un lien symbolique. nginx ne voit jamais un dossier à moitié écrit.

Dépôts privés, sites publics

Une clé de déploiement par dépôt. La source reste privée, le HTML est servi en TLS sur pages.theogalh.dev/<site>/.

Versions atomiques

Chaque déploiement est un nouveau clone superficiel dans releases/<timestamp>. current pointe sur l’une d’elles ; il n’existe aucune fenêtre où un visiteur voit une arborescence partielle.

Webhooks signés

Chaque charge utile est vérifiée contre le secret partagé en HMAC-SHA256 avant que quoi que ce soit ne tourne. Un push sur la mauvaise branche est acquitté puis ignoré.

Un hook raté ? Il se rattrape

Un timer systemd relance le déploiement de chaque site configuré toutes les 10 minutes. Un webhook perdu à cause d’un redémarrage coûte de la latence, pas de la justesse.

Tableau de bord admin

Ajouter un site, voir le commit actuellement servi, redéployer à la main, lire le dernier journal de déploiement dans une fenêtre. Réseau local uniquement, derrière le SSO.

Index qui se recense lui-même

Chaque déploiement régénère la page d’accueil à partir des sites qui possèdent réellement un lien current, donc l’index ne peut pas s’écarter de la réalité.

Un push, de GitHub à nginx

GitHub envoie push sur /webhook/<site>.
La signature est vérifiée ; un site inconnu donne un 404.
La branche est comparée à celle configurée, sinon le push est ignoré.
La réponse part immédiatement ; le déploiement tourne en tâche de fond.
deploy.sh prend un flock et fait un clone superficiel dans un nouveau dossier de version.
ln -sfn déplace current, les versions au-delà de la troisième sont supprimées, l’index est reconstruit.

Architecture

Deux portes d’entrée, une seule fonction de déploiement. Aucune des deux applications ne sait que nginx route par chemin — elles ne connaissent qu’un dossier de destination.

layout
app/
  main.py      webhook: HMAC check, branch match, dispatch
  admin.py     dashboard: list · add · redeploy · logs
  auth.py      OAuth2 + PKCE against TheoAPI, admin role
  deploy.py    run_deploy() — shared by both apps
  config.py    repos.json + env settings
scripts/
  deploy.sh            clone to releases/ + symlink swap
  fallback-pull-all.sh every site, driven by the timer
  generate-index.sh    rebuild /srv/pages/index.html
  update.sh            update self-pages itself
systemd/       webhook · admin · fallback service + timer
nginx/site.conf.example
/srv/pages/<site>/releases/<ts> · current -> <ts>

Décisions

  • Bascule de lien symbolique, pas de git pull sur placeUn pull réécrit le dossier servi fichier par fichier. Un clone à côté plus ln -sfn fait de la bascule une seule opération atomique, et revenir en arrière revient à pointer le lien sur la version précédente.
  • Le webhook répond avant de déployerLe gestionnaire renvoie {"status":"deploying"} et lance le clone en tâche de fond. GitHub obtient sa réponse dans le délai imparti quelle que soit la lenteur du clone.
  • Un timer derrière le webhookLes webhooks fonctionnent au mieux : un redémarrage de service ou un hoquet réseau en perd un sans bruit. Le filet de secours redéploie chaque site à intervalle régulier, donc le pire cas est un retard de dix minutes plutôt qu’un site périmé que personne ne remarque.
  • Un flock par destinationUn hook et le timer peuvent partir au même instant. Le second trouve le verrou pris, dit pourquoi, et sort avec le code zéro — deux déploiements simultanés du même site sont impossibles, pas seulement improbables.
  • Routage par chemin avec une racine dynamiqueUn seul vhost, un seul certificat, un nouveau site n’est qu’un dossier. alias plus try_files gère mal l’index quand le chemin capturé est vide, donc le nom du site passe dans root et un rewrite retire le préfixe ; l’index est résolu par try_files plutôt que par la directive index, qui relancerait la résolution depuis l’URI non réécrite.
  • L’admin n’est pas sur internetElle peut écrire la configuration et lancer git sous l’utilisateur de déploiement, donc elle n’est joignable que depuis le réseau local, par l’IP propre du LXC. Le vhost public ne la relaie jamais, et admin est un nom de site réservé.
  • Du SSO plutôt qu’un second mot de passeLa connexion passe par TheoAPI avec PKCE, et l’application cherche son propre rôle admin dans la réponse userinfo. Un seul compte, un seul endroit où révoquer.
  • La configuration est un fichier JSON, relu à chaque foisAjouter un site depuis le tableau de bord réécrit repos.json ; l’éditer à la main en SSH marche tout aussi bien. Pas de base de données pour une douzaine de lignes.

Le lancer

shell 
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env && cp repos.example.json repos.json
uvicorn app.main:app --host 0.0.0.0 --port 8001
uvicorn app.admin:app --host 0.0.0.0 --port 8090
