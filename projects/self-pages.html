What it does

GitHub Pages does not serve private repositories on a personal plan, and I did not want a build step or a third party in the loop for a handful of static sites. self-pages is the smallest thing that works: GitHub tells it a repo moved, it clones the new commit next to the old one, and flips a symlink. nginx never sees a half-written directory.

Private repos, public sites

A deploy key per repo. The source stays private, the built HTML is served over TLS at pages.theogalh.dev/<site>/.

Atomic releases

Each deploy is a fresh shallow clone in releases/<timestamp>. current points at one of them; there is no window where a visitor sees a partial tree.

Signed webhooks

Every payload is checked against the shared secret with HMAC-SHA256 before anything runs. A push on the wrong branch is acknowledged and ignored.

Missed a hook? It catches up

A systemd timer re-runs the deploy for every configured site every 10 minutes. A webhook lost to a restart costs latency, not correctness.

Admin dashboard

Add a site, see the commit currently served, redeploy by hand, read the last deploy log in a modal. LAN only, behind SSO.

Self-listing index

Every deploy regenerates the landing page from the sites that actually have a current symlink, so the index cannot drift from reality.

A push, from GitHub to nginx

GitHub sends push to /webhook/<site>.
The signature is verified; an unknown site is a 404.
The branch is compared to the configured one, or the push is ignored.
The response returns immediately; the deploy runs as a background task.
deploy.sh takes a flock and shallow-clones into a new release dir.
ln -sfn moves current, old releases past the third are removed, the index is rebuilt.

Architecture

Two front doors, one deploy function. Neither app knows that nginx routes by path — they only know a destination directory.

layout
app/
  main.py      webhook: HMAC check, branch match, dispatch
  admin.py     dashboard: list · add · redeploy · logs
  auth.py      OAuth2 + PKCE against TheoAPI, admin role
  deploy.py    run_deploy() — shared by both apps
  config.py    repos.json + env settings
scripts/
  deploy.sh            clone to releases/ + symlink swap
  fallback-pull-all.sh every site, driven by the timer
  generate-index.sh    rebuild /srv/pages/index.html
  update.sh            update self-pages itself
systemd/       webhook · admin · fallback service + timer
nginx/site.conf.example
/srv/pages/<site>/releases/<ts> · current -> <ts>

Decisions

  • Symlink swap, not git pull in placeA pull rewrites the served directory file by file. A clone next to it plus ln -sfn means the switch is a single atomic operation, and rolling back is pointing the link at the previous release.
  • The webhook answers before it deploysThe handler returns {"status":"deploying"} and runs the clone as a background task. GitHub gets its response inside the timeout no matter how slow the clone is.
  • A timer behind the webhookWebhooks are best effort: a service restart or a network blip drops one silently. The fallback re-deploys every site on a schedule, so the worst case is a ten minute delay rather than a stale site nobody notices.
  • flock per destinationA hook and the timer can fire at the same moment. The second one finds the lock taken, prints why, and exits zero — concurrent deploys of the same site are impossible, not merely unlikely.
  • Path routing with a dynamic rootOne vhost, one certificate, a new site is a directory. alias plus try_files mishandles the index when the captured path is empty, so the site name goes into root and a rewrite strips the prefix; the index is resolved through try_files rather than the index directive, which would restart resolution from the un-rewritten URI.
  • The admin is not on the internetIt can write config and run git as the deploy user, so it is reachable only from the LAN, over the LXC's own IP. The public vhost never proxies it, and admin is a reserved site name.
  • SSO instead of a second passwordLogin goes through TheoAPI with PKCE, and the app checks for its own admin role in the userinfo response. One account, one place to revoke.
  • Config is a JSON file, re-read every timeAdding a site from the dashboard rewrites repos.json; editing it by hand over SSH works just as well. No database for a dozen rows.
